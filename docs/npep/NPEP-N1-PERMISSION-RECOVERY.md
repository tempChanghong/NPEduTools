# N1 源码权限故障后的恢复顺序

本文件是修复准入与交接记录，不是立即重跑许可。现场旧版已经恢复健康；NPEP 保持关闭，PM2 部署代理及三个 GitHub 发布入口保持暂停。

## 已确认的问题

Codex 首次升级命令的全局 `umask 077` 使 root 检出的源码成为 600，Docker 复制后 node 用户无法读取 `scripts/npep-config.js`，现场退出码为 1、错误 EACCES。配置卷本身正常；没有 N1 迁移记录或 NpepDeployment 表。详见 [事件证据](NPEP-N1-FIRST-DEPLOY-INCIDENT.md)。

## 修复与验证

1. 前端仍冻结在 `37a3f1b01585fd8cfc751c921668a84d5c41264f`，本次优先只改后端部署流程。
2. 修复后端镜像中应用源码的可读性，保留 root 所有权，不通过改成 root 运行解决。宿主机 `.env`、数据库备份、存档权限不放宽。
3. 将 env、生产备份、部署运行记录及数据库 dump 等排除在构建上下文外，不能在复制进镜像以后再删除来代替排除。
4. 用假的私有文件和受限源码权限构建隔离测试镜像：证明普通 node 用户可读启动代码、不可写源码、镜像不含假私有文件；不使用真实学校数据或密钥。
5. 在隔离数据库验证原始容器 CMD 与 readiness，补齐配置检查、迁移、应用启动链的证据。原先 CI 单独通过 helper 或在容器外启动应用，不能代替这一项。
6. 就绪失败时，在回退删除失败容器之前保存诊断。只保存固定 inspect 字段及有界日志，日志目录 700、文件 600；不把 Env/Args 或原始日志回显到公开记录。脱敏不能保证覆盖任意日志秘密，保留结果仍作为私有材料。
7. 对修复提交运行相关本地检查及托管质量检查。提交变化后不能沿用旧 e660876 的成功结果称新版本通过。

## 再次交付服务器命令时必须处理的细节

- 给出修复后的完整后端 SHA；先核对发布工作流仍禁用，再决定 main 的受控快进。不能直接开放自动部署。
- 保存第一次失败的 rollback-state 与升级记录，避免下一次升级覆盖唯一证据。现有旧版镜像标签、离线存档与最新备份继续保留。
- 日志目录以私有权限创建；升级子流程使用明确的源码权限策略。单改 umask 不会修复旧文件，镜像修复必须通过上述受限权限回归。
- 从旧 checkout 调用旧 upgrade.sh 时，新提交中的诊断补丁不能保证在这次执行中生效。必须在外围接管“失败取证 → 核对本轮回滚状态 → 应用回退”，或使用经审查的独立驱动；不能继续使用旧版自动回退把失败容器先删掉。
- 失败处理只回退应用，不自动还原数据库。任何迁移状态变化需要先调查；当前没有还原数据库的依据。
- 成功后验证实际容器镜像、两仓 HEAD、NPEP=false、readiness，再由现场核实登录、作业、通知、学校管理。通过后才按既定顺序恢复部署代理与 GitHub 发布入口。
